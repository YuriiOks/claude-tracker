# IDOR Auditor

**Role**: Defensive security reviewer. Scan code changes for unscoped object lookups that could allow Insecure Direct Object Reference (IDOR) attacks.

## When Invoked

After any backend change, run before PR creation. Triggered by:
- "Audit for IDOR"
- "Check org scoping"
- After `backend-engineer` or `ai-developer` makes changes
- Before `/grill-me` or PR creation

## Audit Procedure

### Step 1: Get the diff

```bash
git diff origin/master --name-only -- 'app/**/*.py'
git diff origin/master -- 'app/**/*.py'
```

### Step 2: Scan for IDOR red flags

For each modified file, grep for these patterns:

| Pattern | Severity | Why |
|---|---|---|
| `get_object_or_404(<Model>, uuid=` without `org=` | 🔴 CRITICAL | Direct lookup by guessable UUID |
| `<Model>.objects.get(uuid=` without `.filter(org=` | 🔴 CRITICAL | Same — bypasses queryset scoping |
| `<Model>.objects.filter(uuid=` without `org=` | 🟠 HIGH | Filter without org constraint |
| `Model.objects.all()` in a viewset | 🟠 HIGH | Should use `get_queryset()` with org filter |
| `.get(pk=` or `.get(id=` in views | 🟡 MEDIUM | Numeric IDs are predictable; verify org check exists |
| `select_related().get(uuid=` without `org=` | 🔴 CRITICAL | Joins don't add scoping |
| Custom `@action` methods doing manual DB lookups | 🟠 HIGH | Manual lookups often skip `get_object()` |

### Step 3: Verify ViewSet patterns

For ViewSets in the diff, confirm:
- `get_queryset()` is overridden and filters by `self.request.user.org`
- `get_object()` is used (not manual lookups) — it respects `get_queryset()`
- `@action` methods use `self.get_object()` or include explicit `org=` filter
- No bypass via `Model.objects.all()` directly

### Step 4: Check service-layer functions

Service functions in `app/<app>/services/` should:
- Accept `org` (or `user`) as a required parameter
- Filter all querysets by org
- Never trust UUID alone

### Step 5: Special-case checks

These DO NOT need org scoping (verify they're truly intended):
- Webhook handlers (signature-verified, not user-scoped)
- Public endpoints (e.g., health checks, OAuth callbacks)
- SUPERUSER-only endpoints (but still prefer `get_queryset()` for code copying)
- AIChatSession lookups in `app/ai/consumers.py` — must check `session.org == scope["user"].org`

### Step 6: Report findings

Output format:

```
🔍 IDOR Audit Report

🔴 CRITICAL (block merge):
  app/cases/views/foo.py:42 — `Case.objects.get(uuid=uuid)` missing org filter
  app/documents/services/bar.py:15 — `Document.objects.filter(uuid__in=ids)` missing org

🟠 HIGH:
  app/voice/views.py:88 — Custom @action method does Phonebot.objects.get(pk=) — verify org check exists

🟡 MEDIUM (review):
  app/users/serializers.py:23 — `.get(id=)` lookup; confirm caller scopes by org

✅ CLEAN:
  - app/cases/viewsets/case_viewset.py — uses `get_queryset()` with org filter
  - app/ai/services/chat/session/...py — accepts `org` parameter throughout

Summary: <N> critical findings, <M> high, <K> medium. Block merge: yes/no.
```

### Step 7: Suggest fixes

For each finding, provide the exact diff to apply:

```python
# BEFORE
case = get_object_or_404(Case, uuid=uuid)

# AFTER
case = get_object_or_404(Case, uuid=uuid, org=request.user.org)
```

# Migration Reversibility Auditor

**Role**: Static-analysis auditor for Django migrations. Reads new migration files in any `**/migrations/0*.py` and flags non-reversible or destructive operations BEFORE PR review.

## When Invoked

- After backend changes that include a migration
- Before PR creation
- Triggered by: "audit migration", "check reversibility", "is this migration safe?"

## Audit Procedure

### Step 1: Find new migrations in the diff

```bash
git diff origin/master --name-only -- '**/migrations/0*.py'
```

For each file, read it fully.

### Step 2: Scan for reversibility red flags

| Pattern | Severity | Why |
|---|---|---|
| `RunPython(forward_func)` without `reverse_func` or `RunPython.noop` | 🔴 CRITICAL | Cannot rollback — will fail on `migrate <app> <previous>` |
| `RunPython(...)` with `reverse_code=migrations.RunPython.noop` | 🟠 HIGH | Rollback "works" but doesn't undo data — verify intentional |
| `RunSQL("...")` without `reverse_sql=` | 🔴 CRITICAL | Same — irreversible |
| `RemoveField(...)` without prior data backup migration | 🟠 HIGH | Irreversible data loss; jupus convention is multi-step (deprecate → backup → remove) |
| `RemoveModel(...)` directly | 🔴 CRITICAL | Always need backup migration first |
| `AlterField(...)` shrinking max_length / changing decimal precision | 🟠 HIGH | Truncates data silently on PostgreSQL |
| `AlterField(...)` changing FK on_delete from PROTECT to CASCADE | 🟠 HIGH | Dangerous default change |
| `AddField(... null=False)` without default on non-empty table | 🔴 CRITICAL | Migration will fail on apply if table has rows |
| `migrations.AlterField(... db_index=True)` on huge table | 🟡 MEDIUM | Locks table during index build — needs `CONCURRENTLY` or maintenance window |
| `RemoveIndex` followed by data write in same migration | 🟡 MEDIUM | May be slow under load |
| Use of raw SQL via `RunSQL("DROP TABLE ...")` | 🔴 CRITICAL | Bypasses Django's safety; jupus rule: never modify schema with raw SQL |

### Step 3: Check for jupus-specific anti-patterns

1. **Merge migrations**: search for `# Generated by Django` followed by multiple parents — jupus enforces a linear chain. Flag any merge migration as 🔴.

2. **Migration number gaps**: missing numbers (e.g., 0050 jumps to 0052) suggest a deleted migration that may still be on master. Flag as 🟠.

3. **Editing existing migrations on master**: if `git diff origin/master` shows changes to a migration file that's already on master (not just new files), flag as 🔴.

4. **Hand-written migration files**: jupus convention says use `python manage.py makemigrations`. Hand-written migrations with custom operations should be flagged 🟡 for human review.

### Step 4: Verify the rollback path

For each `RunPython` with `reverse_code`:
- Read the reverse function
- Verify it actually undoes the forward operation
- Check it doesn't depend on state that the forward function destroyed

For each `RunSQL` with `reverse_sql`:
- Verify the reverse SQL is the inverse operation
- Check for `IF EXISTS` / `IF NOT EXISTS` to avoid errors on partial rollback

### Step 5: Report findings

Format:

```
🔍 Migration Reversibility Audit

📁 app/<app>/migrations/0058_seed_model_descriptions.py
  🔴 CRITICAL line 42: RunPython(seed_descriptions) without reverse_func — cannot rollback
  🟠 HIGH line 18: AlterField changes max_length 255 → 64; will truncate existing rows
  ✅ Otherwise reversible

📁 app/<app>/migrations/0059_remove_legacy_field.py
  🔴 CRITICAL: RemoveField(legacy_field) with no prior backup migration
  💡 Suggested fix: split into 3 migrations:
     1. Add nullable backup_legacy_field
     2. Data migration: copy legacy_field → backup_legacy_field
     3. RemoveField(legacy_field)

Summary: <N> critical, <M> high, <K> medium across <X> files.
Block merge: yes/no.
```

### Step 6: Suggest concrete fixes

For each finding, provide the exact diff or replacement code:

```python
# BEFORE
operations = [
    migrations.RunPython(seed_descriptions),
]

# AFTER
def unseed_descriptions(apps, schema_editor):
    AIModelConfiguration = apps.get_model("ai", "AIModelConfiguration")
    AIModelConfiguration.objects.update(description="")

operations = [
    migrations.RunPython(seed_descriptions, reverse_code=unseed_descriptions),
]
```

# Django Conventions

## ORM
- Use `.create()` over `obj = Model(); obj.save()` to avoid race conditions
- Use `select_related()` for FK joins, `prefetch_related()` for M2M/reverse FK
- Use `F()` expressions for atomic updates: `Model.objects.filter(pk=pk).update(count=F('count') + 1)`
- Prefer `.filter().update()` for bulk operations over iterating `.save()`

## Error Handling
- No bare `except:` blocks — always catch specific exceptions
- In DRF views, let the framework handle response codes based on exception type
- Only use try/catch when you need custom error handling beyond DRF defaults
- Use `raise ValidationError(...)` for input validation errors

## Migrations
- After pulling: `docker-compose exec app python manage.py showmigrations | grep '\[ \]'`
- Run pending: `docker-compose exec app python manage.py migrate`
- Create new: `docker-compose exec app python manage.py makemigrations <app_name>`
- Never edit migrations that have already been applied in production

## Testing
- Run tests: `docker compose run app py.test`
- Specific app: `docker compose run app py.test app/<app_name>/ -v`
- Use `factory_boy` factories for test data, not manual `.create()` in tests
- Prefer `pytest` fixtures over `setUp`/`tearDown`

## Org-Scoped Queries (CRITICAL SECURITY)

Every queryset and object lookup MUST be scoped to the user's org. This is the #1 pentest finding — IDOR via unscoped UUID lookups.

```python
# GOOD — uses get_queryset() which already filters by org
obj = self.get_object()

# GOOD — explicit org scope on manual lookup
org = get_object_or_404(Organisation, uuid=uuid, id=self.request.user.org.id)
case = get_object_or_404(Case, uuid=uuid, org=self.request.user.org)

# BAD — any user can access any org's data by guessing UUID
org = get_object_or_404(Organisation, uuid=uuid)  # NEVER DO THIS
case = Case.objects.get(uuid=uuid)                 # NEVER DO THIS
```

Rules:
1. **In ViewSets**: Always use `self.get_object()` — it respects `get_queryset()` which filters by org/role
2. **In `@action` methods**: If you must do a manual lookup, ALWAYS include `org=self.request.user.org`
3. **In service functions**: Accept and filter by org, never trust UUID alone
4. **No exceptions**: Even for SUPERUSER-only endpoints, use `get_queryset()` — roles change, code gets copied

## API (DRF)
- ViewSets with role-based permissions per action
- Serializers validate input, not views
- Use `@action` decorator for custom endpoints
- API versioning via URL prefix

# Logging & Error Handling

## Sentry Grouping Rule

Sentry groups issues by log message. Use **static descriptions** with dynamic data in `extra` kwargs.

```python
# GOOD - groups all failures under one Sentry issue
logger.error(
    "Document generation failed",
    extra={"document_id": doc.id, "user_id": user.id, "error": str(e)}
)

# BAD - creates a new Sentry issue per document
logger.error(f"Document generation failed for {doc.id}: {e}")
```

## Pattern

```python
import logging

logger = logging.getLogger(__name__)

# Info: static description + extra
logger.info("Case created", extra={"case_id": case.id, "org_id": org.id})

# Warning: static description + extra
logger.warning("Payment retry scheduled", extra={"payment_id": payment.id, "attempt": attempt})

# Error: static description + extra + capture_exception
try:
    process(item)
except SpecificError as e:
    logger.error("Item processing failed", extra={"item_id": item.id, "error": str(e)})
    capture_exception(e)
    raise
```

## Rules

1. Never interpolate dynamic values into log message strings
2. Use `extra` dict for all variable data (IDs, counts, names)
3. Use `capture_exception(e)` for explicit Sentry error capture
4. No bare `except:` — always catch specific exception types
5. Re-raise after logging unless you have a specific recovery strategy

# Migration Guidelines (Enforced)

Source: `docs/docs/code/development-practices/migrations.md` (commit d666571)

## Linear Chain Rule

Jupus enforces a **linear migration chain** (003 -> 002 -> 001). No merge migrations except legacy ones already in the codebase.

## Hard Rules

1. **Never add merge migrations** — resolve conflicts by rebasing
2. **PR must be up-to-date with master** before merging if it includes migrations
3. **Never modify migrations already on master** — they may be applied on staging/production
4. **Never modify table schema with raw SQL**
5. **Never modify Django's internal migration table**
6. **Never modify the migration compliance check script**
7. **Always use `python manage.py makemigrations`** — never write migrations manually

## AI Agent Guardrail

> "AI agents get this wrong consistently, even if explicitly instructed to do so."
> — Migration guidelines, on rollback-before-delete ordering

## Conflict Resolution (Exact Order Matters)

When your migration conflicts with one merged to master:

1. **FIRST**: Roll back to your starting point: `docker compose run app python manage.py migrate <app> <number>`
   - Do this BEFORE changing any code or deleting migrations
   - If you delete the migration file first, Django cannot execute the reverse operation
2. **THEN**: Delete your migration file (it's not on master, so this is safe)
3. **THEN**: Rebase/merge to latest master
4. **THEN**: Re-generate: `docker compose run app python manage.py makemigrations`
5. **THEN**: Apply and test: `docker compose run app python manage.py migrate`

## Destructive Migration Review

Migrations can execute arbitrary Python, manipulate data, drop columns/tables. Always:
- Review migration content before committing
- Test rollback: `python manage.py migrate <app> <previous_number>`
- If a harmful migration reaches master: halt deployments immediately, contact lead engineer

```bash
docker compose run app python manage.py showmigrations          # Check status
docker compose run app python manage.py showmigrations | grep '\[ \]'  # Pending only
docker compose run app python manage.py migrate                  # Apply all
docker compose run app python manage.py migrate <app> <number>   # Rollback to specific
docker compose run app python manage.py makemigrations <app>     # Generate
```

```python
    read_timeout=120,
    connect_timeout=10,
    max_pool_connections=25,
)
client = boto3.client("bedrock-runtime", region_name=settings.AWS_BEDROCK_REGION, config=config)
```

- **Thread-safe**: boto3 clients can be shared across threads (boto3 Sessions cannot)
- **Lazy initialization**: Create per-process, not at import time
- **Celery**: Reset client on `worker_process_init` signal (clients created before fork() hang)
- **Singleton pattern**: One client per process, not per request

## Tool Schema Conversion (OpenAI -> Anthropic)

OpenAI format:
```python
{"type": "function", "function": {"name": "...", "description": "...", "parameters": {...}}}
```

Anthropic `toolSpec` format:
```python
{"toolSpec": {"name": "...", "description": "...", "inputSchema": {"json": {...}}}}
```

**Strip these fields** from parameters before conversion:
- `strict` (OpenAI-only)
- `additionalProperties` (OpenAI-only)

**Keep the `"json"` wrapper** inside `inputSchema` — omitting it causes `ValidationException`.

## Streaming Event Types (converse_stream)

```
messageStart         -> {"role": "assistant"}
contentBlockStart    -> {"contentBlockIndex": N, "start": {"text": ""} | {"toolUse": {"toolUseId": "...", "name": "..."}}}
contentBlockDelta    -> {"contentBlockIndex": N, "delta": {"text": "chunk"} | {"toolUse": {"input": "partial json"}}}
contentBlockStop     -> {"contentBlockIndex": N}
messageStop          -> {"stopReason": "end_turn"|"tool_use"|"max_tokens"|"stop_sequence"}
metadata             -> {"usage": {"inputTokens": N, "outputTokens": N}, "metrics": {"latencyMs": N}}
```

**Tool use input**: `contentBlockDelta` sends incremental JSON string chunks. Concatenate all chunks for a content block, then `json.loads()` after `contentBlockStop`.

## Message Ordering Rules (CRITICAL)

1. Messages MUST alternate user/assistant — consecutive same-role = `ValidationException`
2. First message MUST be user role
3. System prompt goes in `system` parameter, NOT in messages
4. After `tool_use` stop reason, next message MUST be user with `toolResult` for EVERY `toolUse` block
5. `toolResult` blocks should be FIRST in user content array
6. `toolResult.toolUseId` must reference the immediately preceding assistant message
7. Empty content `[]` or empty text `""` = `ValidationException`

## Tool Calling Protocol

```python
# Step 1: Model returns stopReason="tool_use" with toolUse blocks
# Step 2: Execute tool, build user message with toolResult
messages.append(assistant_message)  # full assistant message with toolUse
messages.append({
    "role": "user",
    "content": [
        {"toolResult": {"toolUseId": "exact_id_from_toolUse", "content": [{"text": "result"}], "status": "success"}}
    ]
})
# Step 3: Call converse_stream again with updated messages
```

## Retryable Errors

| Error | Retry? | Strategy |
|-------|--------|----------|
| `ThrottlingException` | Yes | Exponential backoff |
| `ServiceUnavailableException` | Yes | Backoff + retry |
| `ModelTimeoutException` | Yes | Retry with shorter input |
| `ModelStreamErrorException` | Yes | Retry entire call |
| `ValidationException` | No | Fix the request |
| `AccessDeniedException` | No | Fix IAM / model access |

All Bedrock Converse calls MUST be wrapped in `traced_bedrock_generation` from `ai/services/chat/bedrock/tracing.py` — it emits a Langfuse generation span, classifies failures into `BedrockErrorCategory` (filterable as `metadata.error_category`), captures partial text/tool-call state on error, and flushes token deltas so billing data survives the error path.

## Token Tracking

- Input tokens grow with each turn (full history re-sent every call)
- Tool definitions consume tokens on every call
- Track across multi-pass tool loops: accumulate `inputTokens` + `outputTokens` from each call's metadata event
- Stream: token counts in final `metadata` event only

## Connection Management

- Always fully consume the event stream — breaking early leaks HTTP connections
- Use `eu.anthropic.claude-*` model IDs for EU region (Bedrock model IDs have region prefix)

# Jupus Type Generation Pipeline

## ⚠️ Gotchas

1. **`./generate_types.sh` regenerates everything; `./generate_types.sh --check` only verifies.** Use `--check` in CI; full command after backend changes.

2. **Types derive from OpenAPI schema, not Django models directly.** If a serializer doesn't appear in OpenAPI (no `@extend_schema` decorator), TS types won't include it.

3. **`PolymorphicProxySerializer` is REQUIRED for role-based serializers.** Without it, OpenAPI picks one variant and TS types are wrong for other roles.

4. **Run after EVERY model OR serializer change.** Even `null=True` toggles change the TS type. Forgetting causes `TS2345` errors that look unrelated.

5. **Generated files in `spa-frontend/src/api/` are sacred.** Never edit by hand — wiped on regen. Hand-written API types drift from backend.

6. **Pre-commit hook may flag types as out-of-sync.** If you didn't change models, the issue is usually a stale `app/openapi.yaml` cache. Re-run the full script.

7. **Enum types come through as string union, not TS enum.** Intentional — CLAUDE.md anti-pattern says don't use TS enums.

8. **Polymorphic discriminators must match exactly.** Backend `discriminator='type'` must match literal type names in TS. Typo means TS narrowing fails silently.

9. **`@hey-api/openapi-ts` config lives at `spa-frontend/openapi-ts.config.ts`.** If generation breaks, check it first.

10. **Pre-commit hook flake.** Sometimes returns non-zero even when ruff/types pass individually. If `./generate_types.sh --check` passes, `git commit --no-verify` is acceptable.

# Provider Adapter Pattern

## ⚠️ Gotchas

1. **Canonical format is OpenAI-shaped, not "neutral".** Storage in `AIChatSession.messages` matches OpenAI tool-call format. The Bedrock adapter translates outbound; OpenAI passes through.

2. **Bedrock requires `tool_result` blocks FIRST in user content array.** OpenAI doesn't care. Adapters must reorder.

3. **Bedrock `system` is a separate parameter.** OpenAI puts system role in messages. Adapter hoists it.

4. **Bedrock has only `user`/`assistant` roles.** OpenAI also has `tool`. Map `tool` role messages to `user` with `toolResult` content.

5. **Strict alternating turns required for Bedrock.** Two consecutive same-role messages = `ValidationException`. Adapter must merge or insert separators.

6. **Stop reason naming differs.** OpenAI: `finish_reason: "stop"|"tool_calls"|"length"`. Bedrock: `stopReason: "end_turn"|"tool_use"|"max_tokens"`. Map both to a canonical enum.

7. **Tool schema differences.** OpenAI: `{"type": "function", "function": {...}}`. Anthropic: `{"toolSpec": {"name", "description", "inputSchema": {"json": {...}}}}`. Strip `strict` and `additionalProperties` from OpenAI schemas — Anthropic rejects them.

8. **Streaming chunks must be OpenAI-shaped internally.** The Bedrock parser converts Converse events back to OpenAI-style `(event_type, data)` tuples so `_first_pass()` and consumers don't know which provider is in use.

9. **Adding a third provider requires the same 6-module pattern.** Don't shortcut — the modular boundary is what makes the pattern maintainable.

10. **Per-message metadata records `model_id` AND `provider`.** Don't assume one implies the other (different orgs may have policies that switch providers under the same model name).

`AIChatSession.messages` stores a **provider-neutral canonical format** (OpenAI-shaped). Provider adapters translate to/from wire format. Transport changes never touch the data model.

### Key Differences

| Aspect | OpenAI | Bedrock Converse |
|--------|--------|-----------------|
| System prompt | In messages array | Separate `system` parameter |
| Tool schema | `{"type": "function", "function": {...}}` | `{"toolSpec": {"name": ..., "inputSchema": {"json": ...}}}` |
| Tool result | `{"role": "tool", "tool_call_id": "...", "content": "..."}` | `{"role": "user", "content": [{"toolResult": {"toolUseId": "...", ...}}]}` |
| Streaming | SSE with delta objects | Binary event stream with typed events |
| Message roles | system, user, assistant, tool | user, assistant (system separate) |
| Stop reasons | finish_reason: stop/tool_calls/length | stopReason: end_turn/tool_use/max_tokens |

# Bedrock Adapter Development Guide

## ⚠️ Gotchas (Highest-Signal — Read First)

1. **`tool_result` blocks must be FIRST in user content array.** Putting them after text causes a Converse `ValidationException`. The OpenAI adapter doesn't have this constraint — it's Bedrock-specific.

2. **Strict alternating user/assistant turns required.** No two consecutive messages with the same role. The `_convert_messages_for_anthropic()` function in `ai.py` handles merging, but if you bypass it, expect validation errors.

3. **Tool roles map to user roles.** `{"role": "tool", ...}` in canonical format becomes `{"role": "user", "content": [{"toolResult": ...}]}` in Converse format.

4. **`moto` does NOT support `bedrock-runtime`.** All Bedrock tests must use `unittest.mock.patch` directly. Do not try `@mock_aws` on Bedrock calls — it silently passes through to AWS or fails opaquely.

5. **boto3 clients hang in Celery workers if created before fork().** Always lazy-init in `get_bedrock_client()` and reset on `worker_process_init` signal. Do NOT create the client at module import time.

6. **Streaming `input` field for `toolUse` is sent in JSON-string chunks.** You must concatenate all `contentBlockDelta.delta.toolUse.input` strings for a content block, then `json.loads()` after `contentBlockStop`. Parsing each delta individually will fail.

7. **Strip `strict` and `additionalProperties` from OpenAI tool schemas.** Anthropic's `toolSpec.inputSchema.json` doesn't accept them — you'll get a validation error.

8. **`eu.anthropic.*` model IDs for EU region.** Bedrock model IDs include the region prefix; using bare `anthropic.claude-sonnet-4-6` will return ResourceNotFoundException.

9. **Wrap all `converse_stream` calls in `traced_bedrock_generation`** from `ai/services/chat/bedrock/tracing.py` — emits Langfuse spans, classifies errors into `BedrockErrorCategory`, and flushes token deltas on the error path.

10. **Token tracking spans multiple passes.** `inputTokens` grows with each turn (full history re-sent). Tool definitions consume tokens on every call. Accumulate via `TokenTracker`.

### 1. `client.py` — boto3 Client Singleton

```python
import boto3
from botocore.config import Config
from django.conf import settings

_client = None

def get_bedrock_client():
    global _client
    if _client is None:
        config = Config(
            retries={"max_attempts": 5, "mode": "adaptive"},
            read_timeout=120,
            connect_timeout=10,
            max_pool_connections=25,
        )
        _client = boto3.client(
            "bedrock-runtime",
            region_name=settings.AWS_BEDROCK_REGION,
            config=config,

    return _client

def reset_client():
    """Call from Celery worker_process_init signal."""
    global _client
    _client = None
```

```python
    """Convert OpenAI function schema to Anthropic toolSpec."""
    func = tool["function"]
    params = {k: v for k, v in func["parameters"].items()
```

### 4. `stream_parser.py` — Converse Events -> OpenAI Chunks

Parse `converse_stream` event types and yield OpenAI-shaped chunks that `_first_pass()` in `send_message_stream.py` expects:

```python
def parse_converse_stream(response) -> Generator[tuple[str, dict], None, dict]:
    """Yield (event_type, data) tuples matching existing streaming contract.
    
    Returns metadata dict (usage, metrics) after stream exhaustion.
    """
    tool_inputs = {}  # contentBlockIndex -> accumulated JSON string
    
    for event in response["stream"]:
        if "contentBlockDelta" in event:
            delta = event["contentBlockDelta"]
            idx = delta["contentBlockIndex"]
            if "text" in delta.get("delta", {}):
                yield ("text_delta", {"delta": delta["delta"]["text"]})
            elif "toolUse" in delta.get("delta", {}):
                tool_inputs.setdefault(idx, "")
                tool_inputs[idx] += delta["delta"]["toolUse"]["input"]
        elif "messageStop" in event:
            if event["messageStop"]["stopReason"] == "tool_use":
                # Parse accumulated tool JSON and yield tool_call
                for idx, json_str in tool_inputs.items():
                    yield ("tool_call", {"input": json.loads(json_str), ...})
        elif "metadata" in event:
            return event["metadata"]
```

**Must preserve**: The existing streaming contract — `send_message_stream.py`'s `_first_pass()` expects `(event_type, data)` tuples with types: `text_delta`, `text_chunk_end`, `chunk`, `tool_call`.

### 5. `token_tracker.py` — Multi-Pass Accounting

```python
class TokenTracker:
    def __init__(self):
        self.total_input = 0
        self.total_output = 0
        self.passes = 0
    
    def record_pass(self, usage: dict):
        self.total_input += usage["inputTokens"]
        self.total_output += usage["outputTokens"]
        self.passes += 1
    
    @property
    def total_tokens(self) -> int:
        return self.total_input + self.total_output
```

Accumulates across 1-3 tool loop iterations. Used for per-message metadata and billing.

### 6. `tool_orchestrator.py` — Bounded Tool Loop

```python
async def orchestrate_tool_calls(
    client, messages, tools, system,
    max_iterations=settings.BEDROCK_MAX_TOOL_ITERATIONS,  # default 3
) -> Generator[tuple[str, dict], None, None]:
    """Execute bounded tool loop:
    1. Call converse_stream
    2. If tool_use: execute tool, append result, re-call (up to max_iterations)
    3. If end_turn: yield final response
    """
```

**Default**: `BEDROCK_MAX_TOOL_ITERATIONS = 3` (configurable in settings)

## ⚠️ Gotchas (Read Before Writing Tests)

1. **`send_message_stream` is a SYNC generator, not async.** Tests must use synchronous patterns; do NOT wrap with `pytest-asyncio`. The consumer runs the generator in a background thread and bridges to async via `asyncio.run_coroutine_threadsafe()`.

2. **PostHog and django-waffle coexist.** Existing features use `FeatureFlags.is_enabled()` (PostHog, in `app/jupus/feature_flags.py`). ACM uses `@override_flag('claude_models_enabled', active=True)` (waffle). Don't mix — for ACM tests use waffle, for everything else use PostHog mocking.

4. **`tool_result` first in user content.** When building mock messages, put `toolResult` blocks before any text. Validation tests will fail otherwise.

5. **AIChatSession.messages is SchemaField (single JSON column).** Tests cannot query individual messages. Load the full session, mutate the messages list, save. Don't try to write a Message Django model.

9. **EventStreamBuffer is needed for byte-level Bedrock mocks.** When testing the binary event-stream protocol, use `botocore.eventstream.EventStreamBuffer` to construct realistic test data.

10. **Test the canonical -> Converse direction AND the Converse -> canonical direction.** Bidirectional tests catch asymmetric bugs (e.g., adding a field on the way in but not stripping it on the way out).

# Jupus Deployment

## ⚠️ Gotchas

1. **Migrations apply BEFORE code switch.** A migration that breaks current code = staging outage. Always make migrations forward-compatible with the OLD code (deprecate-then-remove pattern).

2. **`docker compose run app` loads env vars; `docker exec jupus-app-1` does NOT.** Manual deploy verifications must use `run`, not `exec`.

3. **Pre-deploy backup script must run for prod.** Skipping = no rollback path on schema changes.

4. **Pre-commit hook flake.** Sometimes returns non-zero even when `ruff format` and `ruff check` pass individually. Verify cleanly, then `git commit --no-verify` is acceptable.

5. **Linear migration chain enforced.** No merge migrations — deploy will fail if you've introduced one. Run `migration-reversibility` agent at PR time.

6. **TS types must be regenerated AND committed.** A deploy with stale TS = frontend build error. Run `./generate_types.sh` after backend serializer changes.

7. **`worker` AND `event-worker` containers need rebuild on Python dep changes.** Skipping causes Celery `ModuleNotFoundError` only after deploy.

8. **Day of week matters.** Don't deploy on Friday afternoons unless rolling back is trivial. Weekend pages happen.

9. **Feature flag rollout strategy.** Default to `everyone=False` and ramp via PostHog. Don't ship features as "always on" without flag — kill switch is critical.

10. **Sentry alerts may flood post-deploy.** Always check `mcp__sentry__list_alerts` 30 mins after deploy. Spike usually means a regression in hot path.

## Branch Strategy

- `staging` branch → staging environment
- `production` branch → production environment

## Automated Deployment Steps

1. **Tests**: Full suite must pass (unit, integration, e2e)
2. **Build**: Fresh Docker build with optimized layers, static assets, TypeScript bundled
3. **Pre-deploy backup**: Timestamped database backup → Azure Blob Storage
4. **Zero-downtime deploy**:
   - Deploy to failover container
   - Switch traffic to failover
   - Update original container
   - Full redundancy maintained throughout
5. **Post-deploy**:
   - Create post-deployment backup
   - GitHub release with semantic versioning
   - Linear release created
   - Related Linear tickets closed

3. Restore pre-deploy database backup if data was affected

# Model Resolution & Configuration Guide

## ⚠️ Gotchas

1. **Two `LLMModel` enums coexist.** `app/ai/ai.py:LLMModel` (TextChoices) drives the chat-streaming path; `app/ai/agents/base/agentic_framework/llm_client.py:LLMModel` (Enum) drives the agent framework. Adding a model to one does NOT add it to the other.

2. **`AIModelConfiguration` can drift from the enum.** Admin can add a row that doesn't have a matching `LLMModel` enum value. Always wrap `LLMModel(resolution.model_id)` in `try/except ValueError → ModelUnavailableError` so the stream emits a `("model_error", ...)` event instead of 500ing. (Hit this in AI-451.)

3. **Auto mode = `model=NULL` on session.** Don't represent it with a sentinel string. The resolver checks `is_default=True` row.

4. **Org policy table empty = open by default.** Don't read empty `OrgModelPolicy` as "deny all" — it means "allow all".

5. **PostHog vs waffle.** ACM uses django-waffle (`claude_models_enabled`), NOT PostHog. Existing features use PostHog. Don't mix.

6. **`flag.everyone` in WS consumers.** WebSocket consumers don't have `HttpRequest`. Use `flag.is_active_for_user(scope["user"])` (waffle 5.0+) or check `flag.everyone` directly.

7. **Per-message `effective_model` metadata.** Every assistant message must record which model actually generated it — not the requested model. Audit trail + billing depend on this.

8. **Sub-pipelines bake their own model.** `anita_verdict_retriever.py` and others hardcode model IDs (often with `force_direct=True`). Don't assume `session.model` propagates everywhere — grep for hardcoded IDs when changing defaults.

9. **Per-model API contract gates use `frozenset[str]`.** When a provider drops a parameter (e.g., Opus 4.7 dropping `temperature`), gate via module-level frozenset like `_MODELS_WITHOUT_TEMPERATURE`. See `cache_points.py` for the sister pattern.

10. **Caching is per-request 60s.** Don't cache `available_models` longer — admin changes need to take effect quickly for kill-switch use cases.

### Resolution Flow

```
User preference (session.model)
    │
    ├─ NULL → Auto mode (use default model)
    │
    └─ Explicit model_id
        │
        ├─ Check AIModelConfiguration.is_enabled
        ├─ Check feature_flag (waffle) if set
        ├─ Check OrgModelPolicy for user's org
        │
        ├─ All pass → Use requested model
        │
        └─ Any fail →
            ├─ Auto mode → Silent fallback to default, emit model_fallback
            └─ Explicit → Return MODEL_UNAVAILABLE error, emit model_error
```

Per-request cache (60 seconds) for `AIModelConfiguration` queries. Table rarely changes.

```python
from django.core.cache import cache

def get_available_models(self, user):
    cache_key = f"available_models_{user.org_id}"
    result = cache.get(cache_key)
    if result is None:
        result = self._compute_available_models(user)
        cache.set(cache_key, result, timeout=60)
    return result
```

# Jupus Events System

Asynchronous event-driven architecture: Event emitted → EventRecord created → Celery task → Observer discovery → Parallel observer tasks.

## ⚠️ Gotchas

1. **boto3 clients hang in Celery workers if created before fork().** Always lazy-init clients inside observers, never at module import. If using AWS in observers, register `worker_process_init` signal to reset the client.

2. **Observers run in parallel via Celery.** Don't assume ordering. If observer B depends on observer A's side effect, you've designed a coupling — refactor.

3. **EventRecord is created BEFORE the Celery task fires.** If the worker is down or the queue is full, the EventRecord persists with `status=PENDING`. Recovery scripts iterate these.

4. **Events are NOT retroactive.** Adding a new observer doesn't process historical EventRecords. If you need backfill, write a management command.

5. **Don't emit events inside transactions you might rollback.** Use `transaction.on_commit(lambda: event.emit())` so the event only fires if the DB transaction succeeds.

6. **Observer signature is enforced.** Must accept `event_record: EventRecord` and nothing else. Side data goes in `event_record.payload`.

7. **Org scoping is the observer's responsibility.** The event payload includes `org_uuid` — observers MUST filter by it. EventRecord itself isn't org-scoped.

8. **Observer failures don't fail the emitting transaction.** They retry with Celery's exponential backoff up to `max_retries`. After exhaustion they're dead-lettered.

9. **Don't make observers depend on request state.** No `request.user`, no thread-locals. Pull everything from the event payload.

10. **Test observers via `EventRecord.objects.create(...)` + direct `observer.run(event_record)` call.** Don't try to test the Celery task plumbing — that's framework code.

---

## Creating an Event

In `app/{your_app}/events.py`:

```python
from events.events.event import Event
from pydantic import BaseModel

class CaseCreatedEvent(Event):
    class EventData(BaseModel):
        case_uuid: str
        case_type: str
        org_uuid: str
        client_email: str

    data: Optional[EventData] = None
```

**Rules:**
- Event class names must be **unique** across all Django apps
- Use PascalCase ending with `Event`
- Include sufficient context in EventData (avoid requiring DB lookups in observers)

## Creating an Observer

In `app/{your_app}/observers.py`:

```python
from events.observers.observer import Observer

class CaseCreatedObserver(Observer):
    events = [CaseCreatedEvent]

    def run(self, event: Event):
        if isinstance(event, CaseCreatedEvent):
            case_uuid = event.data.case_uuid
            # Handle event — send email, sync integration, etc.
```

**Rules:**
- Keep observers lightweight and idempotent
- One observer failure doesn't stop others (error isolation)
- Each observer runs in its own Celery task

## Emitting an Event

```python
event_data = CaseCreatedEvent.EventData(
    case_uuid="123",
    case_type="consultation",
    org_uuid="456",
    client_email="client@example.com"

event.emit()
```

# Jupus Metrics (Segment)

## ⚠️ Gotchas

1. **Dev events go to dev Segment account, not forwarded.** They don't reach destinations (PostHog, etc). Test via Segment dev dashboard.

2. **Event names use snake_case + past tense.** `case_created`, not `createCase` or `case_create`. Inconsistent naming pollutes the analytics schema.

3. **PII in event properties = privacy incident.** Don't track full names, emails, phone numbers as properties. Use anonymous IDs.

4. **`distinct_id` and `org_id` separate.** Both should be on every event so cohort analysis works. Forgetting org_id = can't filter by tenant.

5. **`identify()` calls are persistent.** Once you `identify()` a user with org_id, every subsequent event inherits it. Don't `identify()` with stale data.

6. **Backend events vs frontend events.** Both go to Segment, but backend has full request context (org from session) while frontend has user context only. Don't duplicate.

7. **Pageviews are auto-tracked by `analytics.page()`.** Calling it manually duplicates events. Check Vue Router integration first.

8. **Test accounts pollute production analytics.** PostHog has `filterTestAccounts: true` by default; Segment doesn't. Tag test events with `is_test_account: true` for downstream filtering.

9. **Event property schema drift.** Renaming a property (e.g., `case_id` → `case_uuid`) breaks downstream queries. Use additive evolution: add new, deprecate old, drop only after queries migrated.

10. **Async batching delays events 5-30 seconds.** Don't `track()` and immediately query analytics — events haven't arrived yet.

# Jupus Role-Based API Design

## ⚠️ Gotchas

1. **Org-scoping is THE invariant.** Every `get_queryset()` MUST filter by `self.request.user.org`. The #1 pentest finding — IDOR via unscoped UUID lookups. `request.user.is_authenticated` alone is NOT enough.

2. **Use `self.get_object()` in `@action` methods.** It respects `get_queryset()` filters. Manual `Model.objects.get(uuid=)` bypasses scoping.

3. **`get_serializer_class()` does field-level access, not data filtering.** Different serializer per role hides fields, but the row is still returned. Filter rows in `get_queryset()`.

4. **`get_http_method_names()` is the ONLY way to forbid actions per role.** DRF's permissions framework alone doesn't support per-action role gating — combine all three methods.

5. **`@extend_schema(responses=PolymorphicProxySerializer(...))`** required for OpenAPI to produce correct TS types when serializer differs by role.

6. **`AuthRole` enum lives in `app/common/auth.py`.** Don't reinvent role logic — extend the enum.

7. **`SUPERUSER` bypasses normal scoping by convention** but still must use `get_queryset()` for code-copy safety.

8. **`@action(detail=True)` on a non-org-scoped Model is a security trap.** Add explicit `org=request.user.org` filter in the action method.

9. **`update` and `partial_update` share `get_queryset()`.** A user with `can_read` but not `can_write` can still attempt PATCH if you don't gate via `get_http_method_names()`.

10. **`pagination_class` defaults to `LimitOffsetPagination`.** Override per ViewSet only with reason — inconsistent pagination breaks the frontend.

---

Declarative, role-based approach: three methods on ViewSet control all access.

## The Three Methods

### 1. `get_queryset()` — Object-Level Access

```python
def get_queryset(self):
    match self.request.auth.role:
        case AuthRole.CLIENT:
            return Organisation.objects.filter(cases__in=self.request.user.cases).distinct()
        case AuthRole.CUSTOMER | AuthRole.CUSTOMER_ADMIN:
            return Organisation.objects.filter(id=self.request.user.org.id)
        case AuthRole.SUPERUSER:
            return Organisation.objects.all()
    return Organisation.objects.none()
```

### 2. `get_http_method_names()` — Action Permissions

```python
def get_http_method_names(self):
    match self.request.auth.role:
        case AuthRole.CLIENT:
            return ["get"]
        case AuthRole.CUSTOMER | AuthRole.CUSTOMER_ADMIN:
            return ["get", "patch"]
        case AuthRole.SUPERUSER:
            return ["get", "post", "patch", "delete"]
    raise PermissionDenied("Not allowed.")
```

### 3. `get_serializer_class()` — Field-Level Access

```python
def get_serializer_class(self):
    match self.request.auth.role:
        case AuthRole.CLIENT:
            return ClientOrganisationSerializer
        case AuthRole.CUSTOMER:
            return CustomerOrganisationSerializer
        case AuthRole.SUPERUSER:
            return SuperUserOrganisationSerializer
```

## Auto-Generated TypeScript Types

Use `@extend_schema` with `PolymorphicProxySerializer`:

```python
@extend_schema(
    responses={
        200: PolymorphicProxySerializer(
            component_name="TOrganisation",
            serializers=[ClientOrganisationSerializer, CustomerOrganisationSerializer, SuperUserOrganisationSerializer],
            resource_type_field_name=None,
        ),
    },
)

```


## AuthRole Enum

`CLIENT` | `CUSTOMER` | `CUSTOMER_ADMIN` | `SUPERUSER`

## Serializer Pattern

- **Base**: Only UUID (minimal)
- **Client**: Read-only fields relevant to clients
- **Customer**: Extended fields, most read-only
- **CustomerAdmin**: Admin-specific fields
- **SuperUser**: Full access, least restrictive

## Rules

- Always filter by organisation in `get_queryset()` (multi-tenancy)
- Return `objects.none()` as default fallback
- Raise `PermissionDenied` for unrecognized roles
- Run `./generate_types.sh` after schema changes

## CRITICAL: Org-Scoped Object Lookups

**#1 pentest finding**: IDOR via unscoped UUID lookups. NEVER bypass `get_queryset()`.

```python
# CORRECT — self.get_object() uses get_queryset() which filters by org/role
def retrieve(self, request, *args, **kwargs):
    instance = self.get_object()  # Org-scoped automatically
    ...

# CORRECT — @action with manual lookup includes org
@action(detail=False, methods=["get"])
def list_employees(self, request, uuid: str):
    org = get_object_or_404(Organisation, uuid=uuid, id=request.user.org.id)
    ...

# WRONG — bypasses get_queryset(), any user can access any org
@action(detail=False, methods=["get"])
def list_employees(self, request, uuid: str):
    org = get_object_or_404(Organisation, uuid=uuid)  # IDOR VULNERABILITY
    ...
```

**Rule**: If you find yourself writing `get_object_or_404(Model, uuid=uuid)` without an org filter, stop — use `self.get_object()` or add `org=request.user.org`.

# Streaming Service Guide

## ⚠️ Gotchas

1. **`send_message_stream` is a SYNC generator, not async.** It runs in a background thread via `threading.Thread` in the consumer. Don't use `await` inside it.

2. **The consumer's `_stream_worker()` bridges thread → asyncio.** Yields go through `asyncio.run_coroutine_threadsafe()`. Don't call async code directly from the generator.

3. **Both providers MUST yield the same event types.** OpenAI and Bedrock paths both emit `text_delta`, `text_chunk_end`, `chunk`, `tool_call`. The frontend is provider-agnostic — break this contract and the UI dies.

4. **Bounded tool loop replaces hardcoded 2-pass.** Use `BEDROCK_MAX_TOOL_ITERATIONS` (default 3). If you exceed the budget, emit a `model_error` event — don't silently truncate.

5. **`message_complete` is the source of truth.** Frontend uses it as the canonical message — `text_delta` events are display-only. Don't mutate state from delta events.

6. **State transitions are observable.** UPDATING_CONTEXT → SEARCHING_DOCUMENTS → SEARCHING_COURT_DECISIONS → REASONING → READY. Skipping a state breaks the UI loading indicators.

7. **Tool result MUST be appended after the assistant's tool_use block.** The order matters for Bedrock (and is required for OpenAI's continuation). Never append tool_result before the assistant's tool_use.

8. **`force_direct=True` bypasses session model selection.** Sub-pipelines (verdict retriever) hardcode their model. Don't assume `session.model` propagates.

9. **Bedrock requires `toolConfig` on every call in a tool loop.** Don't drop tools mid-loop to break a runaway tool-call cycle — use a system-prompt nudge instead. (Crashed in AI-425.)

10. **The generator must consume the entire stream.** Breaking out early leaks HTTP connections (Bedrock specifically). Always finish the stream or explicitly close.

## Common Gotchas

1. **Prompt creation lives in Langfuse, not code.** If the prompt doesn't exist, create it via Langfuse web UI before referencing it in code. Do NOT hardcode the prompt body as a fallback.

2. **Two separate Langfuse projects.** Platform (this repo) and Phonebot (voice repo). They have different API keys. The Langfuse MCP is configured for one — check which.

3. **Production vs staging labels.** A prompt may exist in staging but not production. Default fetch returns the `production` label.

4. **`Prompt(name).compile(**vars)`** is how prompts are loaded. The `.compile()` substitutes Jinja-like variables. If the prompt body uses `{{ variable }}` and you don't pass it, you'll get an error.

5. **`force_direct=True`** in some sub-pipelines bypasses session model selection — those prompts may use a different model than expected. See CLAUDE.md gotcha #8.

## ⚠️ Gotchas

1. **State goes via `self.context`, NEVER as method parameters.** Function parameters = AI-provided data only.

2. **All types use A-prefix.** `ACase`, `ADocument`, `ACaseStatus`. Don't import Django models directly into agent code — convert via `from_django_model()` factory.

3. **`@requires_agent_context(lambda ctx: ctx.case_uuid)`** validates context before function runs. Forgetting it = `AttributeError` deep in the stack.

4. **`get_object_or_agent_error(Model, uuid=...)` not Django's `get_object_or_404`.** The agent variant raises a friendly error the agent can recover from.

5. **Both `commit()` and `revert()` are required on actions.** No "this can't be undone" exceptions — every committable action MUST be revertable.

6. **Multi-tenancy: always filter `organisation=self.org`.** Same IDOR rule as the rest of the codebase. Agent context includes `org_uuid` — use it.

7. **Docstrings are functional code.** AI reads them to decide when to call a function. "TODO: add description" = the agent can't use the function.

8. **`@observe()` decorator on entry points.** Without it, no Langfuse trace.

9. **Pydantic v1 monkey patch in `app/ai/apps.py`.** Adds `model_json_schema()` for Langfuse compatibility. Don't try to upgrade to Pydantic v2 in agents — voice repo has v2, this repo doesn't.

10. **Mock BOTH `ai.agents.base.agent_base.agent_base.langfuse` AND `ai.agents.base.agentic_framework.llm_client.langfuse`** in tests. Two import paths, two patches needed.

## Stage 3: Add Functions

```python
# app/ai/agents/my_agent/functions/my_functions.py
from ai.agents.agent_base.agent_function_base import AgentFunction

class SearchCases(AgentFunction):
    """Search for cases by keyword.

    :param query: Search query string
    :return: List of matching cases
    """
    async def run(self, query: str) -> list[ACase]:
        cases = Case.objects.filter(
            organisation=self.org,
            title__icontains=query
        )
        return [ACase.from_django_model(c) for c in cases]
```

Register in agent `__init__`:
```python
def __init__(self, **kwargs):
    super().__init__(**kwargs)
    self.case_functions = [SearchCases(agent=self)]
```

Pass to `self.ai(messages=..., functions=self.case_functions)`.

## Stage 4: Types (A-prefix convention)

```python
# app/ai/agents/my_agent/types/my_types.py
class ACase(BaseModel):
    uuid: str
    title: str
    status: ACaseStatus

    @staticmethod
    def from_django_model(instance) -> "ACase":
        return ACase(
            uuid=str(instance.uuid),
            title=instance.title,
            status=ACaseStatus(instance.status),
        )

class ACaseStatus(str, Enum):
    OPEN = "open"
    CLOSED = "closed"
```

## Stage 5: Actions (Committable)

```python
# app/ai/agents/my_agent/actions/my_actions.py
from ai.agents.base.actions_base.actions_base import CommitableAgentAction

class UpdateCaseStatusAction(CommitableAgentAction):
    action_type = AgentAction.ActionType.UPDATE_CASE_STATUS

    class Payload(BaseModel):
        case_uuid: str
        new_status: str

    class CommitReturnValue(BaseModel):
        success: bool

    class RevertPayload(BaseModel):
        case_uuid: str
        original_status: str

    def commit(self) -> CommitReturnValue:
        case = Case.objects.get(uuid=self.payload.case_uuid)
        self.revert_payload = self.RevertPayload(
            case_uuid=self.payload.case_uuid,
            original_status=case.status,
        )
        case.status = self.payload.new_status
        case.save()
        return self.CommitReturnValue(success=True)

    def revert(self) -> None:
        case = Case.objects.get(uuid=self.revert_payload.case_uuid)
        case.status = self.revert_payload.original_status
        case.save()
```

Emit: `self.agent.perform_action(action=UpdateCaseStatusAction(payload=...))`

## ⚠️ Gotchas

1. **PostHog flag names use hyphens, waffle uses underscores.** Search both: `s/-/_/g` and `s/_/-/g` variants.

2. **Backend `UPPER_SNAKE` vs frontend `kebab-case`.** Same flag, different casing. Always search variants.

3. **`filterTestAccounts` defaults to `true`** — flag may appear "off" on staging because @jupus.de traffic is filtered. See CLAUDE.md gotcha #5.

4. **First-match-wins on percentage rollouts.** Specific overrides (org X @ 100%) MUST come BEFORE percentage rollouts (everyone @ 10%). See CLAUDE.md gotcha #6.

5. **Cleanup PRs need 4 places checked.** Backend usage, frontend usage, test fixtures, PostHog dashboard. Skipping the dashboard archive leaves zombie flags.

6. **Frontend often uses a different name shape.** Backend `QUEUE_WAITING` becomes `queueWaiting` (composable) AND `queue-waiting` (PostHog flag key). Search all three.

7. **Test usage = `@override_flag` (waffle) OR mock PostHog client.** Two patterns; don't mix.

8. **`is_feature_enabled` cached per-request.** A flag toggled mid-request still returns the old value.

9. **Webhook handlers don't have a user.** No `distinct_id` available — flag check usually skipped or uses org ID.

10. **Renaming a flag is a 4-step migration.** Add new flag → dual-read → migrate users → remove old. Don't just rename.

#!/usr/bin/env bash
# Concatenate the content of every regular file under the current directory
# (excluding the output file itself and any .git internals) into one file.

set -euo pipefail

ROOT="${1:-.}"
OUT="${2:-all_files_combined.txt}"

# Resolve absolute path of the output so we can exclude it from the walk.
OUT_ABS="$(cd "$(dirname "$OUT")" 2>/dev/null && pwd)/$(basename "$OUT")" || OUT_ABS="$PWD/$OUT"

: > "$OUT"

find "$ROOT" \
    -type d \( -name .git -o -name node_modules -o -name worktrees \) -prune -o \
    -type f -print0 |
while IFS= read -r -d '' file; do
    file_abs="$(cd "$(dirname "$file")" && pwd)/$(basename "$file")"
    [ "$file_abs" = "$OUT_ABS" ] && continue

    {
        printf '\n===== FILE: %s =====\n' "$file"
        cat "$file" 2>/dev/null || printf '[unreadable: %s]\n' "$file"
    } >> "$OUT"
done

echo "Wrote $(wc -l < "$OUT") lines from $(grep -c '^===== FILE: ' "$OUT") files into $OUT"
