THE PROBLEM

LLMs are expensive & slow

Every token in your prompt is processed every time. A 50K-token system prompt sent 10 times to Opus 4.6 = 500K tokens billed. TTFT scales with prefill length. And in agent traffic, 70–90% of every prompt is identical to the previous one.

Without caching

Every request reprocesses the full prefix. Tools, system prompt, RAG docs, conversation history — all recomputed. Latency dominates. The bill compounds.

TTFT 0.5–5s Full input price TPM eaten fast

With caching

Stable prefix is computed once, then reused. The model skips the prefill and starts generating almost immediately. Per-token cost drops 90%.

ANATOMY OF A REQUEST

The two stages of LLM inference

Every LLM request is two stages stitched together. Caching only helps the first one — but that’s where almost all the latency lives.

1. Pre-fill (the “survey”)

Process all input tokens at once. Every token attends to every other — one massive parallel forward pass through the model. Compute scales O(n²) with prompt length.

Metaphor: an explorer climbs a peak and maps every star in the night sky before taking a single step.

70–85% of total latency measured by TTFT

2. Decode (the “journey”)

Generate one token at a time, autoregressively. Each new token attends to all previous tokens via the KV cache — O(n) per token instead of O(n²).

Metaphor: the explorer walks forward step by step, each step referencing the path behind them.

15–30% of latency measured by TPOT

Key insight: when we say “prompt caching saves 85% of latency,” we mean it skips the pre-fill stage. Decode is unchanged. That’s why caching helps long-prompt workloads dramatically and short-prompt ones marginally.

LAYER 1 · ARCHITECTURAL

The KV cache — what gets cached inside the GPU

The fundamental optimization

Without caching, the n-th token costs O(n²) because K and V for all prior tokens are recomputed each step. The KV-cache stores K and V tensors after they’re computed once, collapsing per-token cost to O(n).

KV_bytes = 2 × L × H_kv × d_head
         × seq_len × batch × dtype

Llama-3-70B at FP16, 8K context: ~2.5 GB per sequence. At batch 32: ~80 GB — exceeds an H100 before model weights.

Why KV reduction matters

LLM decode is memory-bandwidth-bound. An A100’s 2 TB/s HBM means loading 14 GB of weights per token takes ~7 ms; compute takes 0.1 ms. Every byte of KV competes with weights for that bandwidth.

Architectural progression has been brutal:

MHA → MQA → GQA → MLA

~30× KV reduction from 2017 to 2025. DeepSeek MLA: 4–14% of MHA size while outperforming on quality.

This is what happens before any “prompt cache” ever fires. The KV cache is what makes generation O(n) instead of O(n²); prompt caching just exposes that across requests.
ENGINE TRICKS

PagedAttention & RadixAttention

Two ideas that turned LLM serving from research code into production infrastructure.

PagedAttention (vLLM, SOSP ’23)

Pre-vLLM systems wasted 60–80% of KV memory to fragmentation by reserving slabs sized to max_seq_len. PagedAttention treats KV like virtual memory: 16-token blocks allocated on demand, mapped via per-sequence block tables.

2–4× throughput de-facto standard

RadixAttention (SGLang, NeurIPS ’24)

Indexes all live KV pages in a radix tree keyed on token IDs. Finds the longest matching prefix automatically and reuses its KV without recomputation. Cache-aware scheduling reorders requests to maximize hit rate.

5–6.4× throughput shared prefixes
This is what providers expose as “prompt caching”. Anthropic and AWS Bedrock’s prompt cache is a contract over an already-existing engine capability. The API gives you control over what RadixAttention would otherwise do automatically.
THE TAXONOMY

Four caching techniques for LLM apps

When people say “LLM caching” they could mean any of four very different things. Understanding which one solves your problem is half the battle.

1. Semantic caching (application-level)

Embed the user query, search a vector DB for similar past queries, return the cached answer if similarity is above threshold. Skips the LLM entirely.

“Save the whole star map for paths walked before.”

40–70% hit rate ~$0 on hit

2. Prefix caching (provider-level)

Cache the KV state of a stable prompt prefix. The model still runs — but skips the pre-fill computation for the cached portion.

“Set up base camp where trails diverge.”

90% input cost off 85% TTFT ↓

3. Latent instruction priming (provider-level, named variant)

Same mechanism as prefix caching, but applied specifically to system prompts and tool definitions — the “rules and identity” layer that doesn’t change between turns.

“Muscle memory: the explorer doesn’t re-learn how to pitch a tent.”

cachePoint after system block

4. Context distillation (model-level)

Fine-tune the model so the context becomes part of the weights. The shorter prompt produces the same outputs the long one used to. Heaviest commitment, biggest payoff.

“The guidebook becomes the guide — knowledge moves inward.”

requires fine-tuning
What we use today at Jupus: #2 (prefix caching) and #3 (latent instruction priming) via Bedrock cachePoint. What we don’t use yet: #1 (semantic caching) and #4 (distillation). The next big win is probably semantic caching in front of the orchestrator.
SEMANTIC CACHING

When meaning matches

Exact-match caching catches “What’s the weather?” twice but misses “How’s the weather?” Semantic caching catches both. The trick: match on vector embeddings, not strings.

1
Embed the query. User asks “Will the jacket keep me dry?” → vector [0.123, -0.456, 0.789, …] via sentence-transformers (all-MiniLM-L6-v2 is the workhorse: 384 dims, ~22 ms local).
2
ANN search in a vector DB (Valkey + valkey-search, Redis, OpenSearch). Find the nearest cached vector by cosine similarity.
3
Threshold check. If similarity ≥ 0.85–0.95, return the cached response. Skip the LLM entirely.
4
On miss, hit the LLM normally and asynchronously cache the new (query, embedding, response) tuple.

When it shines

  • Customer support: “reset password” / “forgot password” / “can’t log in”
  • FAQ & documentation Q&A
  • Generic shopping assistants (“recommend running shoes”)
  • Hit rates of 40–70% are realistic on real chat traffic

When it bites

  • Personalized responses (“track my order”)
  • Real-time data (stock prices, weather)
  • Legal / medical / financial — false-positive risk
  • Banking case study: 99% FP rate at threshold 0.7
The mitigation pattern: threshold ≥0.95, extract state filters (color, size, price range, user intent) and AND them with the vector search. “Recommend black shoes” stays separate from “recommend white shoes” even though their vectors are nearly identical.
SEMANTIC CACHING · IN PRACTICE

Making it production-grade

Vector similarity alone produces hallucinations at the cache layer — "black shoes" and "white shoes" embed nearly identically. Production systems pair similarity with structured state filters, tenant isolation, and TTL hygiene.

The state-extraction trick

Before embedding, parse the query and extract structured filters. Use them as a WHERE clause alongside vector similarity. This is what the AWS Databases-for-AI team called the difference between a demo cache and a production one.

# user: "recommend white shoes under $80" state = { "color": "white", "category": "shoes", "price_max": 80, "intent": "recommendation" } # match = vector ≥ 0.95 AND state matches

Production stack

  • Vector DB: Valkey + valkey-search (synchronous write indexing — entries usable immediately, µs read latency)
  • Embedding: all-MiniLM-L6-v2 (384 dims, ~22 ms local CPU inference)
  • Storage: JSON over HASH (native vector arrays, filterable side-fields)
  • Distance: cosine, with normalize_embeddings=True

Don’t cache these

  • “Track my order” — user-specific
  • “Stores around me” — location-personalised
  • Real-time data: stock prices, weather, scores
  • Tool-using queries that need fresh API/DB lookup

Build an is_cacheable(query, state) predicate. PII or location filter present → bypass cache.

TTL + jitter + tenancy

  • TTL with jitter: base + random 0–10% to prevent thundering-herd on expiry
  • Tenant isolation: separate keyspaces per org — prevents cross-org leaks (critical for legal AI)
  • Multi-layer: in-memory LRU → Valkey distributed → semantic vector
  • Proactive invalidation: bust cache on knowledge-base updates, not just on TTL
Real-world ROI: 60% hit rate on a customer-support workload at 10K queries/day → $8,856/year saved on Claude Sonnet, with cached responses at ~25 ms vs ~7 s API call (250× speedup). Numbers from a Percona Valkey case study.
PREFIX CACHING

What’s actually cached?

Common misconception: “the prompt text is cached.” Reality: the KV state — the model’s internal understanding of the prefix — is what’s cached.

What gets stored

For every cached token, the model stores its K and V tensors across all attention layers. That’s the output of the pre-fill stage for that prefix — expensive to compute, cheap to reuse.

prefix_kv = {
  layer_0: (K_tensor, V_tensor),
  layer_1: (K_tensor, V_tensor),
  ...
  layer_N: (K_tensor, V_tensor),
}

Why this matters

  • One byte differs in the prefix → different tokenization → different KV → cache miss
  • The cache is strictly contiguous: tools → system → messages, in that order
  • A change at position N invalidates everything from N onward
  • Cache lives in GPU memory on the provider side — that’s why TTLs exist (KV evicted to free up HBM)

Ordering rule (hard)

1-hour entries MUST precede 5-minute entries in the prefix. Mix them in the wrong order and Bedrock returns a ValidationException. The natural order (tools+system → docs → history) satisfies this.

Simplified Cache Management

When you mark one breakpoint, Bedrock scans backward up to ~20 content-block boundaries to find the longest matching prefix already in cache. Often a single well-placed marker suffices.

The aim: a content-block boundary on every change-rate transition. Get this right and you spend writes on the rarely-changing layers and reap reads on every turn.

PITFALLS

Why your cache isn’t firing

Failure modes are silent. The request succeeds; only the response usage fields tell you it didn’t cache. Watch for these:

1

Volatile content placed before a breakpoint

Timestamp, request ID, user name, datetime.now() in the system prompt. Every request becomes a fresh write at 1.25× input cost — strictly worse than no caching.

2

Prefix not byte-identical

Whitespace, BOM, smart quotes, JSON-key reordering all change the hash. Use json.dumps(sort_keys=True) on tool definitions and freeze toolspecs at module load.

3

Tool reordering mid-array

Inserting a new tool in the middle invalidates the cache for everyone using the old order. Always append, never insert.

4

Below the per-model token minimum

4,096 tokens on Opus 4.5+/Haiku 4.5. Request succeeds; cacheWriteInputTokens returns 0 with no error.

5

TTL mixed in wrong order

5-minute entries placed before 1-hour entries. Bedrock returns ValidationException.

6

Client library strips the TTL field

LiteLLM (issue #20326) strips ttl for Bedrock. Claude Code’s Bedrock integration (issue #32671) hardcodes 5-minute. Verify your library’s actual behavior.

EU · REGIONAL

Caches are region-bound

Prompt caching is automatically enabled wherever the model is available, including all EU regions. The catch: each AWS region maintains its own cache.

Cross-region inference (CRIS)

EU profile eu.anthropic.claude-* routes across eu-north-1, eu-west-3, eu-south-1, eu-south-2, eu-west-1, eu-central-1. Opus 4.5/4.6/4.7 are only available via CRIS in EU.

When CRIS routes you to a different destination region than the previous request, you incur a fresh cache write at 1.25× or 2× input cost.

The workaround

For workloads needing stable hit rates: use a regional (in-region) endpoint instead of CRIS. Accept the +10% per-token premium on 4.5+ models in exchange for predictable hits in a single region.

Monitor CacheWriteInputTokenCount in CloudWatch — sudden spikes typically indicate CRIS rerouting.

AWS warns explicitly: “at times of high demand, these optimizations may lead to increased cache writes.” The cost-stability tradeoff is real and observable.
RATE LIMITS

Caching vs the 25 RPM ceiling

The most under-appreciated lever for rate-limit-constrained workloads — and the most-misunderstood. AWS docs state plainly: “cache hits are not deducted against your rate limit.”

Cache reads — FREE on TPM

Don’t count against TPM. At 80% hit rate, you can effectively process ~5× the tokens of your nominal quota.

Cache writes — count on TPM

DO count at full 1.25× or 2.0× rate — they’re still being processed by the model.

RPM — unchanged

Caching does NOT reduce RPM consumption. Every API call is one request regardless of cache state.

For Jupus EU-region Opus 4.6 at 25 RPM: caching stretches what each of those 25 requests/minute can carry, and TTFT ↓ means each finishes faster — but the ceiling itself only moves with a Service Quotas increase, a switch to Opus 4.5, or Provisioned Throughput.

LAYER 3 · APPLICATION

The cascade — skip the model entirely

Application caches sit in front of the model. A hit eliminates the LLM call entirely — 50–100× latency wins (1–50 ms vs 0.5–5 s) and ~$0 token cost.

L0 · In-memory LRU
Sub-millisecond, ephemeral, per-process
L1 · Exact-match Redis
SHA-256 of canonical prompt. 1–5% hit on raw chat traffic, much higher with prompt fingerprinting
L2 · Semantic vector cache
Embed query, ANN search, threshold ≥0.95. 20–60% hit on FAQ. Beware false positives.
L3 · Provider prompt cache
Anthropic / Bedrock cachePoint — 90% off, 85% TTFT ↓
L4 · LLM call (last resort)
Semantic caching warning: a 2025 banking case study found zero-shot bi-encoders at threshold 0.7 produced up to 99% false-positive rates — cached answers to similar-but-different questions, i.e. hallucinations at the cache layer. Mitigation: start at 0.95+, add cross-encoder reranker as second-stage verifier, namespace per tenant.

KNOWN RISKS

The nine gotchas

Documented in the bedrock-aws.md internal rule. Scan before any system-prompt change.

1. Byte-exact prefix required

Any drift (timestamp, reordered tools, varying UUID) breaks the cache.

2. "ephemeral" silently fails

Converse only accepts "default". "ephemeral" is the legacy InvokeModel naming.

3. Hierarchy cascade

Breakpoint at layer N invalidates N and every breakpoint below. Tool-def drift is the most expensive mistake.

4. json.dumps(sort_keys=True)

Concrete pattern against Python dict ordering drift on tools. Freeze toolspecs at module load, serialize once.

5. Never inject volatile values

Timestamps, request IDs, user names → current user turn only, never the stable layer.

6. Sliding TTL

Each cache hit resets the clock. 5m fine for active sessions, not for users returning >5m later. Hence 1h on system+tools.

7. Sub-1024 token no-ops

(Or 4096 on Opus 4.5+/Haiku 4.5.) Don’t sprinkle markers on tiny messages.

8. Model-switching invalidates

Critical for ACM-024 — users toggling models per chat pay full cache-write every switch. Consider per-session model lock.

9. Trace wrapper required

All Bedrock Converse calls MUST be wrapped in traced_bedrock_generation — emits Langfuse span + flushes deltas on error path.

DECISION TREE

When to use what

1

Is the prefix stable and reused?

Yes → provider prompt caching (Bedrock cachePoint). Place breakpoints at change-rate boundaries: tools (1h), system (1h), docs (5m), history (5m, rolling). Essentially free — one read covers the write penalty.

2

Are full responses reused verbatim?

Templated workflows / evaluation replays / batch backfills → exact-match Redis (skips the model entirely). Safe, zero false positives.

3

Are queries paraphrased?

FAQ / support workloads → semantic caching at threshold ≥0.95 with cross-encoder verifier. Legal / medical / financial — stick to exact match. False positives at the cache layer are hallucinations.

4

Self-hosting?

vLLM with --enable-prefix-caching or SGLang RadixAttention — the engine handles cross-request prefix sharing automatically. Add LMCache when KV exceeds GPU memory.

For Jupus EU Opus 4.6 at 25 RPM specifically: file Service Quotas increase + enable caching to stretch each request + consider Opus 4.5 for 1h TTL + use regional endpoint for stable hits + log cacheReadInputTokens on every response.
