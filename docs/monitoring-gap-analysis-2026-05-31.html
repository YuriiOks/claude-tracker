0. Executive summary

Read this first
  • claude-tracker today is mature: FastAPI + async SQLAlchemy + single-file SQLite, JSONL ingest (~/.claude/projects/**/*.jsonl) via polling + watchfiles live tail over WebSocket, per-repo .claude/ scanning, a drag-drop permissions editor that writes settings.json, and 11 React routes.
  • The single biggest gap is strategic: we reverse-engineer everything from JSONL and completely ignore Claude Code's first-party OpenTelemetry stream (CLAUDE_CODE_ENABLE_TELEMETRY=1). OTel gives version-stable, attributed metrics + structured events that JSONL parsing cannot reliably reconstruct.
  • Most feature gaps vs. Claude-Code-Agent-Monitor (CCAM) are deliberate scope boundaries, not oversights — MASTER_PLAN §11 explicitly declines push/email alerting, config-editing-from-UI, multi-surface clients. This doc triages gaps into three buckets so the plan stays aligned with project intent.
  • Recommended thrust: adopt OTel events-first, metrics-second; surface error/latency/compaction/attributed-cost data unavailable from JSONL today; keep SQLite for Phase 1, with a clearly-gated container upgrade path.
  • Task-5 answer up front: No new DB container is required for Phase 1. A container becomes justified only as a de-risking/scaling choice for OTel metrics (see §6). This is a recommendation pending explicit go-ahead — nothing is being built in this pass.
  • Status as of 2026-05-31: Phases 1–2 (OTel events ingestion + derived panels) and Phase 3 (OTel metrics ingestion) are now implemented on SQLite with no new container — Option A confirmed viable through Phase 3.

1. Current state · consumes vs. doesn't

Sources + gaps

Consumes today (real sources)

  • ~/.claude/projects/**/*.jsonl — startup full ingest + 30s incremental + watchfiles live tail → SQLite (session_summary, live_event, WIP session_hour, subagent_call)
  • Per-repo + global .claude/ folders — agents, skills, commands, rules, hooks, output-styles, memory, settings.json/settings.local.json (permissions, plugins, mcpServers), .mcp.json
  • ~/.claude/plugins/installed_plugins.json (names only); ~/.claude.json (mcpServers only)
  • Git via subprocess (git diff, status --porcelain, branch); gh pr list; Linear GraphQL (needs key); Langfuse (needs keys, only on explicit call — not auto-ingested)
  • JSONL parser emits 5 event kinds: command, delegate, skill, tool, permission. cache_read_input_tokens deliberately excluded from token/cost totals.

Does NOT consume — the gaps

  • OpenTelemetry / OTLP — zero references to CLAUDE_CODE_ENABLE_TELEMETRY / OTEL_* anywhere in the codebase. No OTLP receiver, no metrics endpoint, no time-series store.
  • ~/.claude/cost-tracker.log — settings.cost_log property exists but nothing reads it (dead property; cost comes from JSONL usage/subagent_call only)
  • No API-error / retry tracking, no per-tool latency/duration, no compaction tracking, no commit/PR/LOC metrics
  • No active-time metric, no edit accept/reject-by-language
  • No auth (localhost-only CORS), no alerting, no retention/rollup beyond session_hour, no daily/weekly rollup tables. Frontend has no tests.

4. Implementation plan · phased with verifiable success criteria

5 phases

Each phase is independent of the next. Start Phase 1 with a spike; do not build until the spike passes.

Phase 1

OTel events ingestion — events-first, lowest risk, highest value

  • Spike first: confirm Claude Code's Node OTel SDK emits clean http/json logs to a local endpoint — flag as "verify before building"
  • Add FastAPI receiver POST /v1/logs (OTLP/HTTP json). Decode OTel logRecords → append-only SQLite table otel_event(id, event_name, ts, session_id, prompt_id, attrs JSON, repo)
  • Add UI action "Enable telemetry" that writes the env block into ~/.claude/settings.json (reuse permissions_writer infra): CLAUDE_CODE_ENABLE_TELEMETRY=1, OTEL_LOGS_EXPORTER=otlp, OTEL_EXPORTER_OTLP_PROTOCOL=http/json, OTEL_EXPORTER_OTLP_LOGS_ENDPOINT=http://localhost:8765/v1/logs
  • Privacy defaults: leave OTEL_LOG_TOOL_DETAILS / OTEL_LOG_USER_PROMPTS OFF; expose as opt-in toggles
Success: after enabling + a real claude session, otel_event rows appear; an "Errors" panel lists api_error/api_retries_exhausted; make test green.
Phase 2

Derived event panels — no new ingestion

  • Errors feed: api_error / internal_error / api_retries_exhausted
  • Tool latency: p50/p95 from tool_result.duration_ms
  • Compaction timeline: pre/post tokens per compaction event
  • Edit accept/reject by language: code_edit_tool.decision
  • Skill / plugin / MCP lifecycle panels
Success: each panel renders in BOTH themes; npm run lint + npm run build clean.
Phase 3

OTel metrics ingestion — deferred; DB container decision bites here

  • Decision point: FastAPI owns OTLP decode + delta→cumulative accumulation (Option A) OR add OTel Collector container as de-risking layer (Option B). See §6.
  • Metrics: cost.usage, token.usage, lines_of_code, commit.count, pull_request.count, active_time.total
  • Key hazard: default temporality is delta — naive storage gives wrong cumulative totals. Must implement correct accumulation before shipping.
Success: dashboard cost card matches OTel within tolerance of JSONL-derived; LOC/commit/PR cards populate.
Phase 4 — optional

Hook ingestion channel — lifecycle / awaiting-input

  • POST /api/hooks/event + installer writing SessionStart/Stop/SubagentStop/Notification/UserPromptSubmit hooks
  • Gives ~0ms latency + a real working/waiting/completed/error state machine — the one CCAM strength OTel doesn't cover (no SessionEnd event in OTel)
  • Frame as optional; deepens the write-to-config precedent (see §7)
Success: Live page shows awaiting-input state transitions in real time.
Phase 5 — lower priority

UI richness + cross-cutting hardening

  • Configurable model-pricing table (CRUD) so cost stays accurate as models change
  • Health-score panel
  • Richer Workflow viz: error-propagation, concurrency timeline (extend Graph)
  • Tool-aware session-detail renderers
  • First frontend tests (Vitest)
  • Structured JSON logging + rotation (MASTER_PLAN B5)
  • Retention / rollup job
  • Resolve dead cost-tracker.log property (wire or remove)
  • Mascot page — a Claude/Tabby-style status mascot reflecting live session state (per user request 2026-05-31; deferred to this phase, not built yet)
Success: make test passes including frontend; no orphan settings properties; log rotation confirmed after 7 days.

6. DB container decision · Task-5 answer

Three options — one recommended

The axis is implementation risk, not scale. The principal risk with OTel metrics is delta-temporality accumulation — not data volume.

Option A — RECOMMENDED for Phase 1–2

SQLite-first, no new container

Honors MASTER_PLAN §5 ("SQLite locked, no service to run"). Add otel_event (and later otel_metric) tables. FastAPI owns OTLP/json decode — for events this is append-only and trivial. For metrics (Phase 3), FastAPI must implement delta-temporality accumulation correctly.

Option B — DE-RISKING for Phase 3 metrics

Add OTel Collector container

A lightweight, stateless otel/opentelemetry-collector container receives OTLP from Claude Code, handles decode + batching + delta→cumulative, and forwards a normalized stream to FastAPI. Adds one container; no persistent DB. Justification is risk reduction, not scale.

Option C — ONLY on real escalation

Full time-series stack

OTel Collector + VictoriaMetrics (single-binary, low-ops) or Prometheus + optional Grafana. Justified only if high-cardinality/retention outgrows SQLite, or Phase E multi-device lands. Prefer feeding collector → FastAPI → existing React UI over standing up Grafana.

7. Read-only deviation note

Existing precedent

MASTER_PLAN §11 lists "editing Claude config from the UI" as out-of-scope, but the existing permissions editor already writes settings.json — so writing a telemetry env block (Phase 1) and optionally installing hooks (Phase 4) extends an existing narrow precedent rather than breaking new ground. Keep writes explicit, minimal, and backed-up.

Operational caveat: env changes only take effect on the next claude launch, not running sessions. Surface this clearly in the UI.

8. Risks & spike-before-build list

5 items
Verify before committing Phase 1 design: confirm Claude Code emits clean http/json OTLP (chosen to avoid protobuf dependency) to a local endpoint. Do not assume — spike first.
  • Delta temporality default — OTel metrics use delta by default; naive storage of each push gives wrong cumulative totals. Phase 3 must implement correct accumulation before shipping any metric cards.
  • OTel tool targets are privacy-gated — events carry rich tool targets only with OTEL_LOG_TOOL_DETAILS=1 (off by default). OTel complements, not replaces, JSONL. Do not reduce JSONL collection.
  • Cost from OTel is an estimate — the official docs state this explicitly. Langfuse/Console remain billing-truth. Label cost figures accordingly in the UI.
  • Bind the OTLP receiver to localhost — consider an OTEL_EXPORTER_OTLP_HEADERS bearer token for the local endpoint; at minimum ensure the listener rejects non-loopback connections.
