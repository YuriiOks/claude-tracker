Glassmorphism?

No new layer. Consolidate the two existing material systems (the original liquid-glass declarations plus the later neu-glass-hybrid !important block that currently shadows them) into one material system. Glass only on floating surfaces — topbar, modals, command palette, tooltips — capped at ≤6 simultaneous blur surfaces per viewport, blur ≤16px. Neon glow reserved for KPI numerals and live indicators only. Light theme uses saturated accents, no halos — the dark-theme text-shadow glow treatment doesn't carry over.

5. Do NOT do

  • No Redis, no SSR, no service worker. This is a local single-user SQLite-backed dashboard; none of these solve any hop above and each adds an invariant-breaking dependency (service worker also actively fights the "always show freshest data" goal on a live-events app).
  • Don't lower INGEST_INTERVAL_SEC to "fix" dashboard staleness before R-LAT-8 lands. Ticking the full-reparse loop more often makes hop 2's event-loop-blocking problem worse, not better — freshness must come from incremental parsing, not a shorter blocking interval.
  • Don't reach for Alembic/a migration framework as a latency fix. The schema-drift issue (missing session_summary indexes on the on-disk DB, W1-57-1/V4-BE-26) is real but is a correctness gap, not why the app is slow today — the query patterns that would benefit from those indexes are dwarfed by hops 1/2's blocking-ingest cost at current data volumes. Fix it because it's correct, not to move latency numbers.
  • Don't route-split src/styles.css as a first move. 1. Executive summary

The backend architecture (FastAPI+SQLAlchemy async+SQLite/WAL, to_thread convention, camelCase schemas) is sound where it's been applied consistently — the problem is it isn't applied consistently. Ingest never learned to read only new bytes, so it blocks the event loop and, on a real 4.5–4.7GB corpus, blocks app startup for ~460s (measured). Several "fixed" prior findings (H2, H6, H8, H15) have live regressions in sibling files or this WIP branch. Cost numbers are silently wrong in three independent ways (pricing-table gaps, cache-token mishandling, ingest drops) and shown as ground truth with zero flag. There is no auth on any mutating route, including a live-reachable one that can redirect the owner's own OTel exporter. Tests exist and are decent where they exist, but security-fix regressions (C4, files.py traversal) and the new WIP have zero coverage, and there is no CI at all.

1. Realistic threat model (5 lines)

  1. LAN devices via the Vite proxy on 0.0.0.0:47820 are the biggest real hole: vite.config.js:14-15 (host:true) + docker-compose.yml:71 ("47820:5173", unqualified) proxy /api/* and /ws/* server-side straight to the backend, bypassing the backend's own correct 127.0.0.1:47821 bind — this is deliberate (phone-on-LAN is a wanted feature) but currently means zero auth, so any device on the WiFi (guest, IoT, a compromised laptop) has full read/write.
  2. Malicious markdown in a tracked repo (a plugin-dropped .claude/**/*.md, a cloned third party's README, a crafted docs/*.html) is stored XSS the instant the owner (or a phone-LAN client) opens it — marked.parse() → dangerouslySetInnerHTML with no sanitizer, no href scheme check, and an iframe sandbox="allow-same-origin allow-scripts" that is the textbook escape combo.
  3. DNS rebinding from a website the owner visits is concretely reachable at /ws/live: no Origin check before ws.accept() (backend/app/routers/live.py:56-58), and browsers don't apply CORS to WebSocket handshakes — any tab open on the same machine (or LAN) can silently stream live tool-call/session data.
  4. Fake OTel ingest: /v1/logs and /v1/metrics accept unauthenticated payloads (not proxied via /api, so not LAN-reachable today, but reachable from any page open on the host) and can corrupt cost/token numbers the dashboard shows as real; separately, PUT /api/telemetry's endpoint field is unvalidated, so a LAN attacker can redirect the owner's real Claude Code OTel exporter — including full prompt text — to an attacker host.
  5. Net effect: nothing here is remote-internet-exploitable (LAN-adjacency or an already-open tab is required in every chain), but every mutating endpoint — including the one that rewrites the owner's real ~/.claude/settings.json trust rules — has exactly zero gate today. That's the one thing worth fixing regardless of how low-traffic the threat surface is.

4. What NOT to do

  • No OAuth, user accounts, or JWT infrastructure. This is a single-user tool opened from one person's phone — a static shared token + HttpOnly cookie is proportionate; a login screen or session-expiry system is pure overhead for zero added protection here.
  • No mandatory TLS/HTTPS on the LAN listener. Self-signed cert management on a home network adds real friction (cert warnings on the phone every rotation) for a threat model that doesn't include passive network sniffing as the primary concern (LAN write-access and XSS are).
  • No rate limiting / WAF middleware. There is one user; a slowapi-style limiter solves a multi-tenant abuse problem this app doesn't have.
  • No revoking the LAN-open frontend port. docker-compose.yml:71 and vite.config.js:15 are LAN-open on purpose (phone access) — the fix is gating what's reachable, not reverting a wanted feature back to 127.0.0.1-only (that already happened once and was explicitly re-opened in commit 7c0c4b5).
  • No full CSP rollout as a first move. index.html has two inline <script> blocks (theme bootstrap, neural background) and one inline <style> block; a script-src 'self' CSP silently breaks both today. If a CSP is wanted later, externalize those two scripts first — don't ship a broken CSP as part of this pass.
  • No separate CSRF-token system. The shared-token header/cookie in R-SEC-1 already covers the same ground for a single-client tool; a second CSRF mechanism on top is redundant complexity.
